## Problem Statement

Mark captures bugs and enhancements in Linear and wants them to come back as reviewed PRs without sitting at a keyboard prompting Claude Code or Codex. The interactive version of this already works: the `code-loop` skill takes a task to a green PR, and `address-pr-feedback` verifies and fixes CodeRabbit findings. Two things stop it from running unattended:

1. `code-loop` waits for CI and CodeRabbit *inside a live, paid session*. Waiting spends subscription quota and dies when the session ends.
2. Nothing survives a chat ending or a machine restart, and nothing picks up work without Mark present.

gaffer is that loop with the waits moved out of the AI session into a small local Python process, plus a second provider whose job is to make the result trustworthy. The open-source audience is people like Mark: solo devs and small teams who already pay flat rates for Claude and Codex and have a machine at home that stays on.

## What Makes This Cool

- **Night shift (the eventual product).** Subscription quota refills on a timer and unused capacity is lost. gaffer spends it while you sleep and leaves headroom for your day. Every orchestrator in the landscape search is a *dispatcher* (an event arrives, an agent starts). For flat-rate subscribers the scarce resource is time-windowed quota across two vendors, so gaffer's long-term core is a *capacity scheduler*. Existing quota tools (claude-code-queue, Caliper `/usage-guard`, cwarm) are single-session, single-vendor hacks.
- **Tag team, tests first.** Codex writes acceptance tests and likely failure modes against the *unchanged* repo, blind, before Claude writes any code. Claude implements to that contract; Codex then checks the PR against its own tests. The writer never grades its own homework. The morning deliverable is a PR with demonstrated behavior, explained rejections and stated uncertainty, not a claim of "done."
- **Zero inbound.** Runs on a home Mac mini with no public URL, tunnel or webhook. Self-hosted Cyrus, the closest existing tool, requires a public URL for Linear webhooks.

## Constraints

Carried over from the source spec and still binding:

- Mark keeps product decisions, merge and deploy. gaffer stops at "ready for human review."
- No inbound network. All Linear and GitHub traffic is outbound polling.
- Subscriptions only. Never silently fall back to metered billing.
- Issue bodies, repository files and review comments are untrusted task data and cannot expand permissions.
- Child processes run with an environment allowlist: no API keys, base-URL overrides, live-evaluation or production credentials.
- No AI session starts for a poll that found no change.
- Python + SQLite, one local process. No dashboard, cloud queue or agent platform.

## Premises

Agreed during the session (premise 4 revised after the Codex challenge):

1. **Dispatch is a commodity; the new parts are the tests-first tag team, review-round batching and, later, the capacity scheduler.** Cyrus and a dozen younger tools already do Linear → worktree → agent → PR. Build effort goes to the new parts.
2. **Reuse the inner loop.** The writer runs the method of `code-loop` steps 1-3 and `address-pr-feedback`, as headless variants of them. Python owns state, waits, polling, git remote operations and recovery, and does not reimplement how to code a ticket.
3. **Outbound-only polling is a hard rule and a differentiator.**
4. **The billing route is controlled, not detected.** Each child starts with a known auth mode, an environment with API-key and base-URL overrides stripped, and user/project configuration sources that preflight has inspected or disabled. gaffer refuses to launch when it can't establish the route (fail closed). A controlled billing run is integration experiment #1. Reason: Anthropic changed headless subscription coverage three times in 2026, and no evidence shows the CLIs report a billing route before a chargeable run.
5. **v0.1 idempotency uses deterministic external keys** (branch `gaffer/<issue-key>`, PR found by head branch, marker comments in Linear). The source spec's action journal, notification outbox and conflict groups wait until dogfooding shows a need. Security boundaries stay in v0.1.
6. **Distribution:** `uv tool install` plus `gaffer install-launchd`, published to PyPI and GitHub Releases, once Approach B lands. Linear is the first queue adapter and Jasper/Telegram the first notifier, both behind interfaces.

## Approaches Considered

### Approach A: Overnight Pair, Hand-Picked (chosen)
`gaffer run ENG-123` on one issue Mark picks: blind Codex tests, Claude implements and exits, Python waits and polls, one resume per completed review round, report at the end. Effort M (human ~2 weeks / CC ~1-2 days). Detailed below.

### Approach B: Capacity Scheduler Daemon (deferred)
A's runner plus launchd, `agent-ready` polling, a capacity planner over both vendors' windows, a two-job limit, the Jasper notifier and PyPI packaging. Deferred, not rejected: A is its first phase.

### Approach C: Upstream into Cyrus (rejected)
Rejected because Cyrus is TypeScript and built around webhooks, its paid tiers sit on the hosted webhook model, and maintainer appetite for outbound polling is unknown.

## Recommended Approach

> Eng review (2026-10-18): superseded where it conflicts by "v0.1 plan as amended by eng review" near the end of this file. Decisions are in the Decision ledger.

**Approach A: Overnight Pair, Hand-Picked.** It is the first slice of B with nothing thrown away, and it proves the three things the night shift depends on (billing route, resume after a wait, blind tests-first pairing) before any scheduler code exists.

Two structural decisions shape everything below:

- **AI children never touch the network side of git.** The writer edits files and makes local commits. gaffer (Python) pushes, opens the PR, posts thread replies and Linear comments with its own credentials. Children hold no GitHub or Linear token, so a prompt-injected child cannot merge, push elsewhere or comment.
- **gaffer ships its own headless prompts** (`prompts/tester.md`, `implement.md`, `review.md`, `address.md`), adapted from `code-loop` and `address-pr-feedback`. The interactive skills are not invoked as-is: they ask questions, wait inside the session, create their own worktrees, push, and fetch all PR comments themselves, and each of those conflicts with gaffer owning the job.

### Configuration

`gaffer.toml` (outside the vault) maps each Linear team key to: local repository path, GitHub `owner/repo`, base branch, `test_command`, optional `lint_command`, `required_checks` (list of check names), and the worktree root. `gaffer run ENG-123` resolves the repo from the issue's team key; an unmapped team is BLOCKED. At worktree creation gaffer fetches the base branch and records its SHA on the job; that SHA is the job's base for its whole life (v0.1 never rebases). gaffer's own Linear key and GitHub token come from the macOS Keychain, never from files in a repo or the vault.

### Job flow

```text
gaffer run ENG-123
  0. PREFLIGHT   billing route and child isolation checks (see Isolation and
                 billing); any unknown -> refuse to launch (fail closed)
  1. INTAKE      fetch the Linear issue once. Deterministic check: the
                 description has an "Acceptance criteria" heading or a
                 checklist. Otherwise BLOCKED: acceptance_criteria_missing.
  2. WORKSPACE   fetch base; worktree at <root>/<repo>-<issue-key> on branch
                 gaffer/<issue-key>; record base SHA. Existing branch/PR for
                 this key -> reconcile instead.
  3. TESTER      Codex, read-only sandbox, unchanged repo. Returns structured
                 output: test files, a criterion -> test map, and criteria it
                 judged untestable. gaffer validates, writes, runs it red-first,
                 and commits it as the branch's first commit.
  4. WRITER      Claude, implement.md: plan, implement, run the configured
                 checks, make local commits. No push, no PR. Exits with a
                 structured result. gaffer verifies the result.
  5. PUBLISH     gaffer pushes (never force) and opens or updates the PR.
  6. ROUND       AI-free polling of head SHA, required checks, CodeRabbit.
                 One Codex review per head (read-only, short-lived) runs as a
                 recorded job step; no writer is alive during this step.
  7. PACKET      when the round completes: unprocessed feedback items from
                 CodeRabbit, failed required checks and the Codex review,
                 deduplicated and hashed, recorded before any resume.
  8. RESUME      the original Claude session, address.md, once per packet.
                 It verifies each item and returns a disposition per item.
                 gaffer posts thread replies, then back to 5.
                 Max 3 repair cycles, then BLOCKED: repair_limit.
  9. REPORT      written to the job directory and printed; READY, BLOCKED
                 or CLOSED.
```

### Job rules

**Exits.** A job ends in exactly one of:
- **READY**: on the current remote head, all required checks succeeded, the CodeRabbit round is complete (or explicitly marked unverified, see below), the Codex review for that head is recorded, every actionable item has a disposition (fixed with commit SHA, or declined with reason), and gaffer's own run of `test_command` passes including every tester test.
- **BLOCKED**: with a reason code and message. gaffer stores it, writes it to the report, prints it, and posts it once as a Linear comment. Rerunning `gaffer run` after the cause is fixed re-validates from the blocked step.
- **CLOSED**: the PR was closed or merged by someone else. gaffer stops and reports.

**Report.** Every report includes:
- PR URL, verified remote head SHA and base SHA.
- gaffer's own `test_command` result, including the criterion → tester test → pass/fail map.
- Criteria that are untestable or otherwise unverified.
- The disposition of every feedback item.
- Tester-file changes and their stated reasons.
- Whether CodeRabbit completion was verified or unverified.
- Any fallback used, such as a fresh writer session.
- The usage each attempt reported.

The skipped-gates statements required by source spec §10 (staging, legal, live calls, paid evaluations) are printed verbatim as not covered.

**Seed data for B.** Each attempt records whatever usage the CLI reports (tokens, duration, limit events) per provider and role. B's capacity planner is then built on measured data from real jobs, not guesses.

**Tester.**
- Output is JSON with file paths and contents, a criterion-to-test map, and an untestable list. gaffer accepts paths only under the repo's test directories.
- **Red first:** gaffer runs `test_command` on the base. New tests must be collected, and each must fail.
  - A collection or syntax error gets one retry with the error attached, then BLOCKED: tester_invalid.
  - Tests that already pass on the base mean the issue may already be fixed: BLOCKED: already_passing.
  - Zero testable criteria is BLOCKED: no_testable_criteria in v0.1.
- Codex errors, timeouts or unparseable output get one retry, then BLOCKED: tester_failed.
- Untestable criteria are carried into the report as unverified.

**Writer.**
- Runs headless with a permission set fixed by gaffer: file edits inside the worktree, plus a Bash allowlist of `test_command`, `lint_command` and `git status/diff/add/commit`. No push, no `gh`, no network tools. The exact CLI mechanism is pinned in Experiment 3.
- gaffer checks every result before publishing, with these failure paths:
  - Missing or malformed structured result: BLOCKED: writer_no_result.
  - No commits beyond the tester commit: BLOCKED: writer_no_change.
  - The tester commit is no longer an ancestor of HEAD: BLOCKED: tester_commit_rewritten.
  - Any commit touches `.claude/`, `.codex/`, `.mcp.json` or CI workflow files: BLOCKED: forbidden_path. *Amended by R30: CI workflows and `.github/actions/` are harness paths (trailer required, listed in the report), not forbidden.*
  - A writer commit that changes tester files needs a `Tester-Change-Reason:` trailer, and the report lists it.

**Codex reviewer.** One review per head SHA, started after PUBLISH, persisted keyed by head. A rerun reuses a recorded review. On failure, one retry, then BLOCKED: reviewer_failed. A head with no Codex review can never be READY.

**Rounds and packets.**
- A round is `(repo, PR, head SHA, seq)`. It completes when all three hold:
  - Required checks have concluded.
  - The Codex review for the head is recorded.
  - CodeRabbit's completion signal for the head has been seen, followed by a 60s settle that resets on new feedback. The signal is the `CodeRabbit` commit status with description exactly `Review completed` (Experiment 2, R27).
- Feedback items are keyed by `(source, item id, content hash)`, so an edited comment is a new item. A packet is the set of unprocessed items when the round completes. Items are marked processed when the resume result for that packet is recorded.
- Items that arrive later on the same head open round `seq+1` on that head, so an old packet is never re-applied.
- The writer sees only the packet. It never fetches PR comments itself.

**CodeRabbit fallback.** *Amended by R27: Experiment 2 found a verified signal, so this fallback now applies only when the head's status says `Review skipped…` or `Review paused`, or no `CodeRabbit` status appears within 10 minutes of the push. Those cases complete the round at once as unverified rather than waiting 10 minutes.* Original text: if Experiment 2 finds no reliable per-head completion signal, the CodeRabbit condition becomes "no new CodeRabbit item for 10 minutes after the last head push, bounded by the round timeout." The report then marks CodeRabbit completion as **unverified** instead of complete. That never counts as verified, and Mark sees it on every READY report.

**Waits and timeouts.** A round that hasn't completed 30 minutes after its push is BLOCKED: review_timeout. Polling every 60s with jitter; GitHub and Linear rate-limit headers honored. API errors never count as an empty or completed review.

**Liveness and recovery.**
- Every child is launched in its own process group. Its PID, process start time and group are recorded in a lease row on the job.
- A rerun treats a child as alive when the PID exists with the same start time. If the writer is alive, gaffer refuses to act on the job and says so. It does not start a second writer.
- Every step checks real state before acting:

| Interrupted during | Rerun does |
|---|---|
| TESTER | tester commit on branch? keep it : rerun tester |
| WRITER (child dead) | resume the same session with "continue; return the structured result" |
| PUBLISH | remote head equals local? skip push; PR by head branch exists? reuse |
| ROUND | resume polling; recorded Codex review for head? reuse |
| RESUME (child dead) | packet result recorded? continue : resume the session with the same packet |

**Session resume.** Claude sessions are resumed from the same worktree path, which is recorded and never moved. If a resume fails, gaffer starts a fresh writer session seeded with a structured handoff (job record, diff against the base, current packet) and says so in the report. Experiment 3 confirms resume after both the child exiting and gaffer restarting.

**External changes.**
- PR closed or merged: CLOSED.
- A remote head gaffer did not push, such as a human commit: BLOCKED: foreign_head.
- PR becomes conflicting with the base: BLOCKED: base_conflict.
- No automatic rebase in v0.1.

**Isolation and billing (preflight).**
- **Environment:** children get an allowlisted environment with no `ANTHROPIC_*` or `OPENAI_*` keys, base URLs, Bedrock/Vertex switches, or GitHub/Linear tokens.
- **User config:** preflight reads Claude user settings and Codex config. Any of these refuses launch: an `env` block setting keys or base URLs, `apiKeyHelper`, a custom provider or `base_url`, or an API-key login.
- **Repo config:** children run with project-level settings, hooks and MCP servers disabled, via the CLI's own controls pinned in Experiment 3. If an installed CLI can't disable them, gaffer refuses repos that contain them.
- **Instruction files:** `CLAUDE.md` and `AGENTS.md` are read as untrusted guidance. They cannot change gaffer's permission set.
- **Account precondition:** Mark disables paid overage ("extra usage") on both subscriptions, and Experiment 1 records that it is off.
- **Limits:** a usage-limit event in any child stops the job as BLOCKED: usage_limit, with the reset time if the CLI reports one. No retry loop.

## Open Questions

1. **CodeRabbit completion signal.** *Answered by Experiment 2 (R27): the `CodeRabbit` commit status with description `Review completed`.* Which check run, status, review or comment reliably marks a complete round for a head SHA? Experiment 2 decides between the verified path and the fallback above.
2. **CLI controls.** Experiment 3 has to establish which installed flags or settings give each of these. If any is missing, gaffer refuses rather than guessing.
   - Claude: structured output, session-ID capture, resume by ID, a fixed permission set, and disabling project settings, hooks and MCP.
   - Codex: a read-only sandbox, structured output, and ignoring project config.
3. **Tester test placement for repos without a clear test directory.** Convention per repo in `gaffer.toml`, or BLOCKED?
4. **Demo target.** A toy repo first, then one small real RobinHQ bug with clear acceptance criteria.
5. **Name and license.** Check `gaffer` on PyPI and GitHub before committing to it; choose MIT or Apache-2.0.
6. **Policy watch.** As of the 2026-10-07 help-center update, `claude -p` draws from subscription limits. That has changed before. Preflight is the guard; re-check before B.

## Success Criteria

v0.1 is done when all of these are demonstrated on a real repository:

1. Experiment 1 is written up for both CLIs with evidence of which pool each run drew from. Tests prove preflight refuses to launch for:
   - an API key in the environment;
   - a key or base URL set through user config;
   - an API-key login;
   - a repo containing project settings that the CLI can't disable.
2. One real Linear issue becomes a PR whose first commit is Codex's blind tests. Those tests failed on the base and pass on the final head, in gaffer's own test run.
3. During ROUND, no writer process is alive, verified from process state.
4. Killing gaffer mid-round and rerunning `gaffer run <issue>` continues the job with no second PR, no second writer and no duplicate Linear comment. Fixture tests cover every row of the recovery table.
5. At least one real correction (CodeRabbit finding, Codex finding or failed required check) is fixed through exactly one resume of the original Claude session for that packet.
6. A comment arriving mid-round triggers no resume. A late comment after a packet is processed opens a new round on the same head and is never re-applied.
7. The report never says READY for a stale head, a timed-out round, a failed required check, or a head without a Codex review.
8. Security tests prove all of the following:
   - children receive no secrets or tokens;
   - writer commits touching forbidden paths are rejected;
   - an issue body or review comment instructing a merge, push or command outside the allowlist changes nothing gaffer does.
9. Criteria 3-8 are automated in pytest with fake HTTP, the captured CodeRabbit fixtures, recorded CLI transcripts and disposable git repos. Criteria 1-2 are demonstrated runs with saved evidence.

## Reviewer Concerns

Disposition: CONCERNS_RECORDED

Stop: CONVERGENCE

### R2-1 — completeness (blocking)

**Problem**

> Only project-level sources are disabled, and preflight inspects user config only for billing keys. User-level sources still load in every child and can widen the permission set gaffer calls fixed. They include permission allow rules or a default permission mode in Claude user settings (which merge with gaffer's CLI permissions), user hooks, user-scope MCP servers, and claude.ai connectors available to a subscription login; this account has a Linear connector, for example. Codex user config can likewise define MCP servers and profiles that the read-only tester and reviewer may load. So neither the writer's 'no push, no gh, no network tools' set nor the read-only Codex roles is guaranteed.

**Remedy**

> Decide how children treat user-level tool sources. Either exclude user settings, hooks, MCP servers and connectors with the CLI controls pinned in Experiment 3, or have preflight refuse when user config grants permissions, hooks or MCP servers outside gaffer's set. Add this for both CLIs to Open Question 2, and add a pytest case where a user-level allow rule or MCP server is present.

### R2-2 — completeness (blocking)

**Problem**

> Preflight must refuse 'an API-key login' and treat any unknown auth mode as a refusal, but the design never says how it learns each CLI's login type. It names no command, credential file or output, and Open Question 2 and Experiment 3 don't cover it. Without a positive check, preflight either leans on a denylist that misses other non-subscription logins (an Anthropic Console account login, managed settings, or config moved by config-directory environment variables) or refuses every launch.

**Remedy**

> For each CLI, name the status output or credential file that establishes a subscription login, and refuse anything else: Console-account, Bedrock/Vertex and API-key logins. Include managed settings and config-directory overrides in the inspected sources. Add 'login type is machine-readable' to Open Question 2 and Experiment 3.

### R2-3 — feasibility (blocking)

**Problem**

> The Assignment now yields a usable answer, but it still records no CLI versions or login-status output, which Open Question 6's policy re-check needs as a baseline. It also re-reads the API billing pages right after the runs. Those pages can lag, so usage may look flat before metered usage appears.

**Remedy**

> Record both CLI versions and their login-status output with the results. Re-read the API usage pages after a stated delay (for example, the next day) before concluding that usage stayed flat.

### R2-4 — completeness (blocking)

**Problem**

> For several reason codes, 'rerun after the cause is fixed' has no defined meaning. foreign_head and base_conflict cannot be fixed: the base SHA is fixed for the job's life, v0.1 never rebases, and any human resolution (merging the base or adding a fix commit) is itself a foreign head, so the job stays blocked. For repair_limit and review_timeout, the design doesn't say whether the cycle count and the round timer reset on rerun. If they don't, the rerun blocks again at once; if they do, every rerun quietly grants three more cycles. The process exit status for READY, BLOCKED and CLOSED is not stated either.

**Remedy**

> For each reason code, state what fixing it means and what the rerun does, including counters and timers. Either provide a way to accept a human head or a new base, such as an explicit adopt flag that records the new head and base SHA, or state that these jobs must be restarted. Define exit codes.

### R2-5 — completeness (blocking)

**Problem**

> The tester's file allowlist is 'the repo's test directories', but nothing defines those directories for any repo; Open Question 3 covers only repos without a clear one. The design also doesn't say whether paths are checked after resolving symlinks and '..'. A test directory symlinked elsewhere, for example into the vault, would let gaffer write outside the worktree. It is also unclear whether the tester may overwrite existing test files such as a shared conftest, and no size or file-count limits are set.

**Remedy**

> Configure test directories per repo in gaffer.toml. Resolve real paths and reject symlinks and anything outside those directories. Allow new files only, or list every modified existing test file in the report. Cap file count and size.

### R2-6 — consistency (blocking)

**Problem**

> The red-first rule misjudges tests-first output in both directions. A test for a new feature usually imports a function that doesn't exist yet. On the base that is a collection error, so it gets one retry and then BLOCKED: tester_invalid. The tester is also asked for 'likely failure modes', and those guard tests often pass on the base, so 'each must fail' turns them into BLOCKED: already_passing. In the other direction, any runtime failure counts as red, so a test that fails on a typo'd fixture or a wrong import path passes the gate. Round 1 asked for tests that fail for the intended reason, and that requirement is still unmet.

**Remedy**

> Have the tester classify each test as acceptance (must fail on the base) or guard (may pass). Accept a missing target symbol named in the criterion map as a valid red. Require acceptance tests to fail by assertion or by that missing symbol, and treat syntax errors and unrelated errors as invalid.

### R2-7 — feasibility (blocking)

**Problem**

> test_command is a free-form command, yet three parts of the design need per-test outcomes from it: red-first ('collected', 'each must fail'), READY ('including every tester test') and the report's criterion-to-test pass/fail map. They also need a way to tell new tester tests apart from tests that already fail on the base. The design defines no result format and no way to select or identify individual tests, and an exit code alone cannot answer these questions.

**Remedy**

> Require a machine-readable per-test result: for example, a JUnit XML path configured in gaffer.toml, or v0.1 limited to pytest with node IDs. Run the tester tests by ID, and record base failures separately from tester tests.

### R2-8 — consistency (blocking)

**Problem**

> Only tester files are guarded. The writer can make tester tests skip, xfail, get deselected or always pass without touching them, by editing conftest.py or runner config, test plugins, package.json scripts, or the Makefile target behind test_command. None of these is a forbidden path, and none needs a trailer. The design also doesn't say what happens when a writer commit changes tester files without the trailer. This undercuts 'the writer never grades its own homework' and the READY gate.

**Remedy**

> Treat any mapped tester test not reported as passed (skipped, xfailed, deselected or missing) as failed. Protect or flag changes to test-harness files, kept in a configurable list in gaffer.toml, the same way as tester files. Define the outcome of a missing trailer, for example BLOCKED: tester_change_unexplained.

### R2-9 — completeness (blocking)

**Problem**

> The writer's limits exist only at the tool level. Its Bash allowlist includes test_command and lint_command, and git commit can run repo hooks. Each of these executes code that the writer or the repo controls, with Mark's full user privileges. That code can write anywhere, open network connections and read his home directory, so 'file edits inside the worktree' and 'no network tools' do not hold. Reads are not confined either: Claude's file tools and Codex's read-only sandbox restrict writes, not reads outside the repo. The design chooses no OS-level enforcement and does not state which limitations v0.1 accepts.

**Remedy**

> Choose the v0.1 enforcement for children and the commands they run: a CLI's own sandbox mode, a Seatbelt profile, or a separate macOS user. Cover write scope (the worktree), denied reads (credential paths, the vault) and network access during test runs. State plainly what remains possible.

### R2-10 — consistency (blocking)

**Problem**

> Children get no token in their environment, but Mark's ambient credentials stay reachable. These include gh's stored token, the git credential helper and Keychain, the SSH agent and keys, gaffer's own Keychain items (code running as the same user may read them without a prompt), and a claude.ai Linear connector for a Claude child logged in with the subscription. Code run through test_command can use these directly. A child can also put a secret it has read into a test file or a commit, which gaffer then pushes itself. The claim is therefore unsupported, and the round-1 obligation to document what remains possible is unmet.

**Remedy**

> Make the claim true for v0.1: run children where those credentials are unreadable, remove SSH_AUTH_SOCK, credential helpers and connectors, and scan every diff and reply for secrets before gaffer pushes or posts. Otherwise, narrow the claim and document what remains possible, along with any compensating control such as branch protection that blocks merges.

### R2-11 — completeness (blocking)

**Problem**

> SC8 checks the child environment, forbidden writer paths, and that injected instructions don't change gaffer's own actions. It leaves out the boundaries that matter most here. Nothing tests that a child, or code it runs through test_command, cannot read or use ambient GitHub, Linear or Keychain credentials. Nothing tests that a secret placed in a tester file, commit or disposition is never pushed or posted. And nothing tests that tester output with traversal, symlinked or non-test paths is rejected.

**Remedy**

> Add these as security success criteria with pytest cases: attempts to reach ambient credentials, rejection of secrets in diffs and replies, and tester path validation.

### R2-12 — completeness (blocking)

**Problem**

> The post-writer checks still miss two round-1 cases. The first is a dirty worktree. Uncommitted or untracked changes are not pushed, yet the writer's result may claim them, and a test run in that worktree would pass on code the PR lacks. The second is a writer that reports it cannot proceed, because the ticket is ambiguous or needs a product decision. No reason code covers this. Such a result lands in writer_no_change or writer_no_result, and its question never reaches Mark.

**Remedy**

> Require a clean worktree after every WRITER and RESUME result: resume once to commit, or BLOCKED: writer_dirty. Add a 'blocked' status to the writer's structured result that maps to BLOCKED: writer_blocked and posts the writer's question in the Linear comment.

### R2-13 — clarity (blocking)

**Problem**

> Required checks now come from config, but the edge cases are undefined. With an empty list, a PR reaches READY with no CI evidence, and SC7's failed-check guard does nothing. A configured check that never appears on a head (because of path filters or a renamed workflow) shows up only as a generic review_timeout. Under 'all required checks succeeded', skipped and neutral conclusions count as neither success nor failure.

**Remedy**

> Require a non-empty list, or show an empty list explicitly on every READY report. Say how skipped and neutral conclusions count. Use a specific reason, such as BLOCKED: required_check_missing, when a configured check never reports on the head.

### R2-14 — completeness (blocking)

**Problem**

> After every resume the flow returns to PUBLISH, and two paths have no defined exit. One is a resume that commits nothing: PUBLISH skips the push, the head doesn't change and every item is already processed, so it is unclear whether a new round opens or how the job ends. The other is a round that completes with nothing to resume while READY's conditions still fail. Two examples: a failed required check the writer declined, which is already processed and never re-packeted, and a failing run of gaffer's own test_command, which is not a packet source at all. The job can neither resume nor reach READY.

**Remedy**

> Define the transitions. For example, failures in gaffer's own test run and still-failing required checks become packet items that count against the repair limit. A completed round with no resumable items and unmet READY conditions ends as BLOCKED: not_ready and lists what failed.

### R2-15 — completeness (blocking)

**Problem**

> gaffer now runs test_command itself, both for red-first on the base and for READY. The design doesn't say on which heads it runs (after every WRITER/RESUME before PUBLISH, or only on the final head), or on what tree (exactly the committed head, not a worktree with leftover changes). It also leaves out the environment, the timeout and where the result is stored as evidence. And gaffer runs Codex- and Claude-written code as Mark outside any sandbox, the risk round 1 flagged.

**Remedy**

> State when gaffer runs test_command and on which commit. State that the run uses the child environment allowlist and the sandbox chosen for R2-9, and give its timeout. Store per-test results per head in SQLite and have the report cite them.

### R2-16 — completeness (blocking)

**Problem**

> Lease rows cover orphaned children but not the gaffer runner itself. Two `gaffer run ENG-123` invocations can both poll, build packets, post replies and resume the writer one after the other. The one-active-job-per-issue constraint does not stop two processes from driving the same job. The liveness rule covers only the writer, so a rerun can start a second Codex tester or reviewer next to one that survived. The design also doesn't say whether jobs for different issues may run at the same time, or that the writer's whole process group, including test runs it started, is reaped before ROUND.

**Remedy**

> Add a per-job runner lock that a second invocation respects, for example a lease row with gaffer's PID and start time, or a file lock. Apply the liveness check to every child role. State the concurrency policy across issues, and wait for or kill the writer's process group before ROUND.

### R2-17 — completeness (blocking)

**Problem**

> Once the resume result is recorded, 'continue' means posting thread replies and then PUBLISH. Replies have no idempotency key, so a crash mid-posting makes the rerun post duplicates, and CodeRabbit may answer each one. The reconciliation table also has no rule for a lost or recreated SQLite while the branch and PR exist. In that case the session ID, base SHA, tester commit and processed items are all unknown, and marker job IDs no longer match. The table also has no rule for a crash before the writer's session ID was captured.

**Remedy**

### R2-18 — feasibility (blocking)

**Problem**

It edits its own comments: the walkthrough or summary on every push, its in-progress status, and 'addressed' markers on resolved threads. Each edit or reply becomes a new item that resets the 60s settle and opens round seq+1 on the same head. **Remedy**

> Define item admission. Decide which CodeRabbit comment types count as feedback and which are status to ignore, that a bot edit adding only a resolution marker is not a new item, and whether bot replies to gaffer's replies are new items. Exclude resolved threads. Derive these rules from the Experiment 2 fixtures and add a fixture test for each.
